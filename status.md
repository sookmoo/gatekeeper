# gatekeeper: status

## Goal
Gatekeeper: a central repository for user and role management for multiple services and applications. External systems call it over REST to query authentication and authorisation for users. (User's description, 2026-10-09.)

## Requirements (from user)
- REST API consumed by other applications.
- Final deployment: containerised with Podman, PostgreSQL database.
- Built stepwise: minimal vertical slice first; in-memory DB to start.
- First functionality: CRUD for users and user roles. More to follow.
- CLI supporting the functionality. Front-end later.
- User will provide git.

## Decisions
- Back-end language: C# (ASP.NET Core). Chosen by user 2026-10-09.
- Integration: token-based (JWT, verified by consumers via JWKS). Chosen by user.
- Database: PostgreSQL behind a repository interface; in-memory first. Slice 2 uses EF Core + Npgsql (user decision 2026-10-11), citext for case-insensitive uniqueness, FK cascades, migrations as an explicit `migrate` command.
- Podman 6.1.1 (rootless) is installed; used for the dev/test Postgres containers.
- Git strategy: trunk-based. Protected `main`, short-lived feat/fix/chore branches squash-merged via PR, Conventional Commits, build once and promote the same image (PR CI -> main publish -> staging -> tag `vX.Y.Z` -> production with manual approval). Approved by user.
- Git host: GitHub (CI via GitHub Actions, registry GHCR proposed).
- Deployment: local for now; eventually a single server with Podman + Quadlet.
- Agent setup approved: planner (opus), developer (sonnet), qa (sonnet), security (opus), defined in `.claude/agents/`.
- Repo prepared locally 2026-10-09: `git init -b main`, origin = https://github.com/sookmoo/gatekeeper.git, .gitignore, .gitattributes, .editorconfig, placeholder CI workflow. Nothing committed or pushed yet.
- .NET SDK 10.0.111 is installed locally.
- Pending: front-end language (after slice 1).
- Usernames stay lowercase slugs (user decision 2026-10-10); uniqueness remains case-insensitive.
- Slugs (app, role, username) must not look like GUIDs, because the CLI accepts name or id.
- Planner note (user): add PATCH (partial update) alongside GET/POST/PUT in the API at some point; the CLI `update` commands currently emulate it with GET + PUT.

## Open questions
- Auth model for external systems (tokens/JWT, API keys, OIDC).
- Git remote/branching conventions; deadline; user/system scale.

## Slice 5a: administration UI, login and applications (branch `feat/slice-5a-web`)
- Decisions (user, 2026-10-13): Razor Pages (htmx later, only if needed) in a separate container `Gatekeeper.Web`; admin UI first; keep it very simple; low JavaScript footprint (5a ships none); UI port 5090 on loopback. Self-service for users is a backlog item (needs new API endpoints).
- Design: the UI is a backend-for-frontend. The browser holds only an opaque `HttpOnly`, `SameSite=Strict` session cookie (`gk_session`); the access and refresh tokens live in server memory (`WebSessions`, keyed by SHA-256 of the cookie value; idle 30 min, absolute 8 h, max 1000 sessions, a restart signs everyone out). Every API call carries the signed-in administrator's own token, so the audit trail names the real admin (verified on Quadlet). The access token is renewed under a per-session lock (refresh tokens rotate). The API ending the session (revoked, user deactivated, role removed) sends the browser to `/Login?ended=1`.
- Done: `src/Gatekeeper.Web` (sign in with `refresh:true`, sign out ends the API session, applications list/create/rename/delete with a confirmation page; the reserved app is read-only); antiforgery on every POST (ephemeral keys), strict CSP (`default-src 'none'; style-src 'self'`), `no-store`, framing/sniffing/referrer headers; own sign-in failure throttle per address; `Containerfile.web`, `deploy/quadlet/gatekeeper-web.container` (127.0.0.1:5090, read-only, no capabilities, 256 MiB), `install.sh [api-image [web-image]]`, API unit allows the Host name `gatekeeper-api`, CI builds and smoke-tests the web image and pushes it to `ghcr.io/sookmoo/gatekeeper-web`; `tests/Gatekeeper.Web.Tests` (17: pages need a session, CSRF refused, uniform sign-in failure, cookie flags and no tokens in the browser, security headers, CRUD with confirmation, encoding, reserved app, sign-out, API-ended session, throttle, token renewal, idle/absolute lifetime).
- Bug found by the tests: a `<form action=...>` gets no antiforgery token from the tag helper (sign-out would have been refused); use `asp-page`.
- Verified on Quadlet (2026-10-13): sign in, list, create, delete, sign out; audit rows name the admin.
- 5a review fixes (QA + security, 2026-10-13): `LoopbackGuard` now runs after `StartAsync` (it never fired before, so the UI listened on any interface and the CI smoke test would have hung); sign-in throttle is per (address, username) plus per address, a success clears only its own pair, IPv6 /64 buckets; error handling no longer clears headers/cookies (headers are set in `OnStarting`), API errors map to honest statuses (403/404/429/502/503/504) with fixed texts (nothing the API said is echoed), status-code pages for 400/403/404/429 instead of blank bodies, a bad cursor restarts at page 1, 64-character name limit in the forms; `Gatekeeper:ApiUrl` path prefix kept; config values are validated (no crash on `abc`, shorthand proxy addresses refused); `Web__SecureCookies` (`__Host-` prefix, always `Secure`); signing in again ends the previous API session; web unit `Wants=` (not `Requires=`) the API so an API restart does not sign admins out; `Cross-Origin-Resource-Policy`; test quality fixes (vacuous markup test, sign-out now checks the API, config/guard tests).

## Slice 5b: user kinds and test-user expiry (done, PR #9 merged 2026-10-16)
- Decisions (user, 2026-10-15): add a `kind` field to users with an expiry for test users, before the users UI. Service identities stay a separate entity (clients).
- Design: `kind` is `person` (default), `test` or `shared`. `expiresAt` exists only for `test` users: omitted on create it defaults to 30 days, at most 365 days ahead, must be in the future when set (an unchanged date is accepted, so renaming near the expiry works); turning a test user into another kind clears it, turning a person into a test user gives the default. Only a `person` may hold the `admin` role (assigning it to another kind, or changing an administrator's kind, is a 409; checked under the `AdminGuard` so the two cannot race). An expired test user is unusable like a disabled one: no sign-in, refresh or introspection, and no management access; the row and its data stay, and an admin can extend the date. Access tokens already issued live until `exp` (as for disabling). The access token and introspection response carry `kind`. `GET /v1/users?kind=`, `gk user create/update --kind --expires`, `gk user list --kind`. Migration `AddUserKind` (`kind` text with a check constraint, default `person`; nullable `expires_at`); existing users become persons.
- 5b review fixes (QA + security, 2026-10-15): user updates now run under the `AdminGuard` and read the user inside it (a stale read could overwrite a kind changed meanwhile and leave a non-person holding `admin`); `AdminAccessCheck` also requires `kind=person` (defence in depth); access tokens and refresh sessions of a test user end no later than the account; `bootstrap-admin` refuses a non-person user before changing anything; the kind is exactly person/test/shared in JSON and query (the built-in enum parsers accepted numbers and comma lists like `person, test`; a strict converter plus an OpenAPI schema transformer); `gk --expires` without an offset means UTC; audit detail of user create/update/patch lists `kind`, `expiresAt` and `active` after the change; migration also checks `(kind = 'test') = (expires_at IS NOT NULL)`.
- Accepted: the `kind` claim in an access token can be up to 15 minutes stale after a change of kind (introspection is current); client tokens and tokens issued before 5b have no `kind`, so consumers should require `kind == "person"` explicitly and treat a missing claim as not a person; the admin cache (10 s) can keep access for that long after a demotion; the guard is per process (several API instances would need a database-level rule); a rejected sign-in of an expired user looks like any other failure (by design, no reason is given to the caller).
- Not done: automatic deletion of expired test users (they stay, disabled by time); `active=true` in the list still means only the enabled flag, so it includes expired test users.

### Slice 6d: optimistic concurrency for PATCH/PUT/DELETE (API hardening b, API part)
- Scope: users, clients, applications and roles get a `version` (integer, starts at 1, +1 on every change of the row). Responses carry it in the body (`version`) and as a strong `ETag: "<version>"` on single-resource GET/PUT/PATCH. `PUT`, `PATCH` and `DELETE` accept `If-Match`; a mismatch is 412 Precondition Failed (problem body, fixed text); no header means unconditional, as today (Q6d-1). Stores update with `WHERE id = @id AND version = @expected` (EF concurrency token), which also closes the per-process limit of `PatchGate` for conditional requests.
- Why a version column and not `UpdatedAt`: apps and roles have no timestamp, two writes in one microsecond would collide, and an integer is cheap to compare in both stores. Q6d-2 asks whether to use Postgres `xmin` instead (recommended: no, keeps parity with the in-memory store).
- What bumps the version: changes to the row's own fields only. Role assignments, passwords, secrets and sessions do not (they are separate resources). Q6d-3.
- Migration `AddVersions`: `version bigint NOT NULL DEFAULT 1` on `apps`, `roles`, `users`, `clients`.
- CLI: `gk ... update` keeps sending PATCH without `If-Match` (it does not show a snapshot); optional `--if-version <n>` (Q6d-4, recommended to defer).
- Acceptance: GET returns ETag and `version`; PATCH with the current ETag succeeds and returns the new one; with a stale ETag returns 412 and changes nothing (both stores, and under parallel requests); malformed `If-Match` is 400 (Q6d-1); `If-Match: *` matches any existing row; DELETE with a stale ETag is 412; audit row records the 412 as failure; OpenAPI: `If-Match` header parameter, `ETag` response header, 412 responses, `version` in the four schemas.
- Risks: biggest slice of the hardening: touches domain records (constructor changes across all projects and tests), both stores, and the reserved-app/AdminGuard paths (412 vs 409 precedence: define 404 > 412 > 409/400). Weak ETags (`W/`) from proxies must not match a strong comparison.
